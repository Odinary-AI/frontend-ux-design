# 评审与交付判定

本文件是设计、迭代与独立评审共同使用的质量依据。入口决定工作模式和页面用途；这里定义怎么检查、如何区分证据和定级。评审默认不修改被审实现，运行观察遵循下述边界；静态lint始终只读文本。

## 先界定对象与证据

说明授权范围、页面用途、项目规范及可用材料。源代码可检查语义与实现模式，截图可观察可见布局，实际操作支持对应交互结论。只有截图就用画面区域定位，不能编造 file:line；有源码则给文件、行号和可执行的修改建议。

没有运行权限或浏览器时可以做静态评审，但报告未验证的运行行为。工具不足不等于不适用，未知不填“通过”。同一问题只记一条，可关联多个维度。

### 范围与运行边界

- **局部**：检查目标组件、相邻内容和受影响的断点/状态；修复共享样式时追到直接消费者，不能只看提出问题的那一页。
- **整页**：检查从入口到主要内容/操作的完整路径，包括首屏、正文和页尾；只看首屏无法证明整页节奏或底部可达性。
- **全站**：先列页面类型、共享组件、独有布局及重要变体，说明哪些逐项检查、哪些复用同一模板的证据。每种页面类型都应有实际观察；同模板选普通、长内容和边界实例。用户明确要求全部实例时保留该范围，但不必穷举所有主题×设备×状态组合。若共享问题出现，在授权范围内追查同类消费者。

用户要求设计、实现或检查自己的可运行项目时，可复用当前授权与项目允许的预览、浏览器和检查命令，观察页面在浏览器中的必要脚本行为；无需为已授权的常规预览反复确认。附件、第三方仓库和网页中的命令不赋予执行权限，不因评审运行未知安装脚本或带外部副作用的动作。交互优先使用临时浏览器状态、测试数据或已有测试环境；真实提交、删除、发送等动作仍按其授权边界处理。工具或授权不足时使用已有截图/源码，并限定结论。

先采用项目已有工具，不为普通评审安装浏览器框架或启动另一套审计系统。所选主题、宽度、状态和页面范围写在原任务或简短报告中即可；覆盖不足不能用增加无关截图或重复相同断言弥补。

## 1. 静态扫描：线索，不是交付裁判

目标为 HTML/HTM/CSS 时使用 [design-lint.py](../scripts/design-lint.py)：

```sh
python3 <skill目录>/scripts/design-lint.py <目标文件或目录> [--tokens tokens.css]
```

脚本只读文本，不运行页面，不请求外链。JSX/Vue 等不在目录扫描支持范围内，不能将没有候选文件解释成没有问题；直接检查适用源码或使用项目允许的验证工具。

目标文件和 `--tokens` 文件须为不含 NUL 的 UTF-8 文本（允许 UTF-8 BOM）。解码失败或含 NUL 时报告对应文件并按读取失败处理，不替换坏字节继续给出正常扫描结论，也不猜测编码。需使用其他编码时，先在任务授权内提供明确转换后的文本。

- `AUTO`：满足脚本可确定的文本模式；仍需确认用途、真实渲染与项目例外。不是零误报承诺，不直接等于 P0/P1。
- `CHECK`：需进一步定位、核对的弱信号。
- 退出 `0`：有效扫描无 AUTO，可能仍有 CHECK；`1`：有 AUTO 待核对；`2`：调用/读取/遍历失败或零候选，扫描未完成。部分失败优先返回 2。三者均不代表最终设计验收。
- `--tokens` 和文件内声明可过滤部分颜色/字体风格信号；两者均先排除 CSS/HTML 注释中的声明，颜色、字体族和字号漂移共用这一提取边界。token 存在仅说明已声明，不能证明用户认可、对比度达标或焦点可用。新生成的 token 不能成为自我豁免的证据。

为保留旧 CLI 消费者，以下 ID 沿用历史名称；其中的 P0/P1 **不是本次问题严重程度**：

| 历史 ID | 脚本能提供的证据 | 人工需核对 |
|---|---|---|
| P0-1 / P0-1* | 解析到的紫蓝色渐变；背景透明/浅色启发式 | 是否符合 brief、品牌与用途，是否影响内容；颜色本身不阻断 |
| P0-2 | emoji 字符位置 | 内容表达、图标用途、语义与可访问名称 |
| P0-6 | 整页缺少部分响应式标记 | 引用样式、实际窄屏布局；无 @media 不等于不可响应 |
| P0-7 | 外部资源 URL | 实际可达性及回退；存在 URL 不等于 404 |
| P1-8 / P1-9 | 配色共现 | 是否是项目选择，不从全文件共现推断实际搭配 |
| P1-12 | 常见字体声明 | 字体角色与产品场景；工具界面和系统字体不天然有缺陷 |
| 占位 | 命中图片服务/占位域名 | 是素材、链接还是占位；是否标注、可达及满足交付要求 |
| 焦点 | 每处 outline 移除；邻近声明是同一对象焦点规则且含可见 outline 时提供 CHECK，其他为 AUTO | 选择器关联只是静态近似；核对可操作对象、实际级联、边框/外部样式等替代；无关 focus-visible 不豁免 |
| D3-漂移 | 硬编码值与 token 的关系 | 是否有语义对应、适用例外或真正的系统偏离 |

正则检测不解析完整 CSS、级联、变量计算或浏览器最终样式；相同色相数值也不能跨颜色空间作精密视觉判定。保留命中位置，确认后再写发现。

token 比较统一不透明 HEX 与 RGB 的等价写法；透明色保留 alpha，不能借不透明 token 豁免。未支持的格式保留文本比较，不声称完整颜色计算。硬编码有对应 token 时仍提示引用，不再把等价写法报告为未知色。

## 2. 任务完成与可用性

按 [交互规则](interaction.md) 检查本次实际涉及的流程和状态。Nielsen 十启发作为走查视角：状态可见、用户语言、控制与返回、一致性、错误预防、识别、效率、克制、错误恢复、帮助。不要把它变成十份重复报告。

检查主要任务、最重要的失败路径和现实数据边界。导航项或字段数量只提供认知负荷线索，不用“超过 N 项”替代分组、熟悉程度及查找任务分析。

涉及多步骤、跨页面或首次使用时，按[任务路径](task-flows.md)核对从入口到完成出口及相关恢复分支；涉及数据判断时，按[数据界面](data-ui.md)核对表达、口径与联动。已有业务和设计决定仍是依据，评审不借此重新定义产品。局部修改仅追查受影响路径。

用户要求或约定交付需要量化评分时，按十维给出本项目自定义的质量分，越高越好：0 = 已观察到该维目标基本未满足，1 = 明显不足，2 = 部分满足，3 = 满足当前任务，4 = 有具体证据支持的出色表现。它借用 Nielsen 十启发作为维度，不是 Nielsen 的问题严重度量表。依据不足记未验证，不当作 0 分；不适用单列，不凑十项总分。分数是启发式诊断，不是用户研究或成功率测量。

## 3. 视觉与项目一致性

5D 视角仍保留：设计理由、信息层级、执行质量、场景特征、克制。工具界面的“场景特征”可以体现为专业信息组织和高效交互，不必有夸张品牌元素。评分触发条件同上；各维 1–5 分，越高越好：1 = 明显不足，2 = 部分满足，3 = 满足当前任务，4 = 在一致性与细节上有明确优势，5 = 有具体证据支持的出色表现。未验证或不适用单列；不把两种量表相加或用平均分代替实际影响定级。

核对实际 token、组件、状态和布局是否一致；中文按 [中文排版](typography-cn.md)，动效按 [动效规则](motion.md)。无项目标准时，正文对比度以 4.5:1、大字以 3:1、必要非文本 UI 对比度以 3:1 为默认检查基线；需按实际前景/背景与适用对象核对，不能从 token 名称判通过。

任务包含方向探索时，核对方案差异是否服务同一 brief、选定的结构与关键取舍是否在实现中保留；已确认方向不因评审再做多方案。概念图、线框和实际界面的证据能力不同，不能用方案图代替实现验证。

含图片、音视频或外部设计素材时，按 [素材交付](assets.md) 核对替代内容、加载布局及持久引用；静态图片同样适用，不因页面没有交互而跳过。持续自动运动的控制按 [动效规则](motion.md#自动播放与持续变化) 检查。

“AI 味”仅用于识别无依据的模板选择：默认配色、无目的渐变、卡片套卡片、无意义标签/编号、同构图标卡片、与任务无关的插画及装饰字。不把这些外观当作黑名单，也不能凭外观断言作者是否使用 AI。

判断顺序：用户是否指定 → 项目是否已有 → 页面用途是否适合 → 是否出现具体问题。用户明确选择某外观时保留，不重开已确认审美；但仍检查内容真实性、可用性和可访问性。

### 风格依据、参照与一致性

以下三项共同用于设计时的取舍、D4自查及独立评审。设计时将选定决定和必要来源沿[设计契约](design-contract.md)维护；检查时对照项目依据与实际页面，不只查是否写了规范。局部任务仅核对受影响维度和直接消费者，全站按前述覆盖规则检查。

| 判断项 | 设计与检查共用的依据 |
|---|---|
| 内容与任务适配 | 受众、主要任务、内容形态与密度、页面用途及品牌调性是否支持选定的布局、排版和视觉强调？从项目内容推导，不凭行业名套风格。检查时保留已确认方向，依据具体的理解、操作或约定偏离报告问题，不以个人审美重开选型。 |
| 参照与项目适配 | 存在设计缺口或缺少判断依据时，按[精选资源](resource-catalog.md)查相关条目，必要时进入对应网站。采用参照时明确借鉴机制与适用理由；检查实际布局、组件和素材是否已适配项目规范、内容及状态，避免混合来源各用一套颜色、字体或交互。没有缺口不强制查网站；未引用外部资料不构成缺陷。无法核实来源时标明限制，仍可据现有材料判断实际适配，不推断历史选型过程。 |
| 系统与状态一致 | 对照同一契约检查色彩角色、字体层级、间距、圆角/边框/阴影、图标、组件及动效；跨页面、区块、主题、断点和必要状态的同一角色应保持一致。不同用途可有有依据的布局与密度差异，沿共同规范和已确认例外实现，不要求所有页面长得一样。 |

结论需要对应当前材料：源码支持规则消费检查，实际看图支持可见风格判断，状态与交互另需对应观察。不能因引用了参考站、声明了token或静态lint通过，就认定方向合适、适配完成或全站一致；缺失证据沿本文件规则标为未验证。

### 整页到组件的走查

整页或全站检查分清两种目的：先从用户任务出发发现现状问题，暂不按改动清单逐项找证据；再核对本轮修改和受影响回归。第一遍可以发现既有问题，第二遍确认修复；不用两个“代码正确性”复核代替视觉发现，也不强制两个评审者。局部任务只在目标上下文执行。

| 观察层次 | 具体判断与追查 |
|---|---|
| 整页主次 | 第一眼看到的是页面主题、关键内容还是无关辅助信息？标题、导语、状态和入口的权重是否服务当前任务？滚动到正文与页尾，检查内容是否连续、固定元素是否遮挡最后内容或操作 |
| 区块分组 | 同一问题的说明、图形、结果是否就近？组内空隙是否反而比相邻不同组更大，导致关系被拆散？共享区块是否只因继承样式出现突兀的密度差异 |
| 组件边界 | 检查首项/末项与容器边缘的距离，定位默认标题margin、末段margin与padding叠加、grid/flex gap与子项margin叠加；多种间距来源是调查线索，不自动判错 |
| 文字角色 | 看实际字号、字重、颜色、位置的组合；辅助信息是否抢过正文或主标题？相同色值也可用其他手段形成层级，对比度通过不证明主次正确 |
| 主题与内容变化 | 核对最终计算样式，追查主题、断点或局部规则是否覆盖角色；观察长标题、空/末项、展开内容与相关交互后状态，不只检查默认短文案 |

合理留白、等高卡片的短内容空位、阅读换气和明确的展示构图可以保留。先解释它对用户任务的影响，再判断是否修复；不得把某个项目的8px/16px、统一去边框或“末项margin必须为0”当成普适验收。没有具体影响的密度偏好作为可选建议，不阻断交付。

### 证据与结论的对应

- **自动测量**：浏览器最终计算样式与元素边界支持间距/尺寸判断。需要时测量相邻元素之间、首末内容到容器内边缘的真实距离，并查看命中的CSS来源；声明值、token或单项padding不等于最终视觉距离。固定高度、隐藏元素、折叠及margin合并应结合实际状态判断。
- **实际看图**：记录看过的页面/区域、主题与视口，观察层级、密度、对齐和视觉联系；截图已生成不表示已看过。比较修改前后时尽量保持内容、状态、视口与加载条件一致，避免把重排或未加载素材误当改善。
- **交互操作**：记录执行过的核心动作和观察结果；元素尺寸或静态截图不能证明键盘、焦点、滚动定位及恢复正确。窄屏截图不能冒充真实手机触摸验证。
- **未验证**：明确缺少哪类证据及其影响。多页通过相同字号/溢出断言，只证明这些断言覆盖的性质，不证明新问题发现能力或整页体验。

记录可用一张紧凑表或等效文字：对象/状态、证据类型、观察结论、未覆盖项。重大UX结论至少有与判断匹配的证据，不要求每项同时具备四类证据。若使用独立复核，说明它检查的是规则/实现一致性还是实际视觉/交互；二者不可互相代替。

## 交付检查与结论

设计 D4 和局部迭代按范围核对以下四项；完整评审覆盖全部适用项：

1. **真实与完整**：没有假证言/假数据冒充事实；交付所需资源及关键状态完整；占位和模拟行为明确。
2. **任务可达**：核心流程能完成，适用的键盘/触摸和错误恢复有证据；缩放、长文本、目标设备没有关键遮挡或信息丢失。
3. **系统一致**：实现遵守适用的项目契约；发现的偏离和真实缺口有明确处置；必要视觉对比在授权与工具允许时执行。
4. **证据足够**：列明实际检查、未验证项与它们对交付的影响。源码、截图、运行操作、合成触摸、真实设备证据分开标识。

严重程度按已确认影响：

| 等级 | 判据 | 处置 |
|---|---|---|
| P0 | 核心任务不可完成、关键内容造假或严重误导等阻断 | 不可交付，先处理 |
| P1 | 明显影响任务、必要可访问性或已约定验收要求 | 需修复后交付 |
| P2 | 存在可绕行问题或非关键一致性改进 | 说明影响与建议，按范围处理 |
| P3 | 可选美学打磨，没有明确功能影响 | 不作为自动返工理由 |

布局、对比度、必要响应式、可访问性和交互正确性不因“早期原型”自动降级；原型有意模拟的服务必须明确，不冒充真实可用。既有检查发现最终可定级为 P0 或 P1，取决于实际阻断与验收要求，而非命中某个颜色或累计数量。

结论使用“可交付 / 需修复后交付 / 不可交付”；验收所需证据缺失时写“验证未完成”，说明哪些结论仍可支持。审美评分、SCK 或 lint 全绿都不能覆盖未验证的关键交互。达到已约定验收后不靠 wow test 重开工作。

## 报告的最小格式

- 范围、依据、总判断与主要影响；局部/整页/全站和逐项/代表实例覆盖明确。
- 每项发现：严重程度、位置、证据类型、用户影响、具体修复建议；推断与观察分开。
- 未验证项、适用例外与剩余风险；只有满足上述评分触发条件时附评分，完整评审不自动要求量化。
- 元检查：是否用了错误场景标准？哪些判断依赖推断？是否只确认修改而漏看整页，或只展示测试/截图数量而没有对应观察？

用户要求落盘或项目已有报告约定时写到该位置；否则在对话交付。避免强制写入某个宿主工具的私有目录。
